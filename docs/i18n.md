# Internationalization (i18n) — zh_CN translation pipeline and the RS glossary

Audience: developers adding or changing user-visible strings, and maintainers of the
terminology layer. This documents the D6 track: how English source text becomes a
Simplified Chinese UI, and how `data/terms/` serves UI, help and the future agent (D9)
from one file.

## TL;DR for developers

- Write user-visible strings as `tr( "English source text" )`. Never hard-code Chinese
  (or any other language) in `src/`.
- Chinese lives in `resources/translations/sicnu_zh_CN.ts` — a **tracked** file. The
  compiled `.qm` is generated into the build tree and is **never committed**.
- After adding/changing strings, refresh the `.ts`:
  ```bash
  ninja -C build-dev sicnu_i18n_update   # lupdate over src/app → sicnu_zh_CN.ts
  # ... fill in the new translations in the .ts (unfinished entries are release-blocked) ...
  ninja -C build-dev sicnu_i18n          # lrelease → build-dev/resources/translations/sicnu_zh_CN.qm
  ```
- `tests/test_i18n` fails on: unfinished/empty `.ts` entries, glossary reference breakage,
  or unwrapped user-visible string literals in the audited modules.

## Runtime behaviour

The application selects its UI language at startup, in this order:

1. A nonempty `SICNU_LANG` environment override.
2. `preferences/uiLanguage` in the application's SICNU `QSettings`.
3. The system UI language.

The desktop initializes its QGIS profile before reading this preference, then
installs translations before providers and widgets are created. This ensures
startup and Preferences use the same profile INI store, including on Windows.

The supported preference/override values are `system`, `zh_CN` and `en`.
`system` follows the OS UI language; Chinese resolves to Simplified Chinese and
other languages use the English source text. Preferences changes take effect
after restarting the application. An environment override takes precedence over
the saved preference until that override is removed.
An unsupported saved value follows the system language; an unsupported explicit
launch override falls back to English.

Chinese startup loads both the product `sicnu_zh_CN.qm` and Qt's
`qtbase_zh_CN.qm` for standard widgets and Qt-provided dialogs. Catalog lookup:

1. `$SICNU_TRANSLATIONS_DIR` (tests/CI override)
2. `<binary dir>/resources/translations/` (build tree layout)
3. `<binary dir>/../resources/translations/`
4. `<binary dir>/translations/`

These application-relative directories serve both build and installed layouts.
Runtime does not fall back to a developer Qt installation: both catalogs must be
available through the application paths or the explicit translation-directory
override. If either required catalog cannot be loaded, startup keeps both
translators uninstalled and uses English source text throughout, avoiding a mixed
product/standard-widget language.

`lrelease` runs as a build-time dependency of the `sicnu_geo_rs` target (`sicnu_i18n`),
so a plain GUI build produces a current product catalog and copies the configured
Qt kit's `qtbase_zh_CN.qm` into `resources/translations/`. CMake locates that kit's
catalog with the imported `Qt6::qmake` target's `QT_INSTALL_TRANSLATIONS` query;
it does not select a second Qt installation from `PATH`. Only the explicit
`qtbase` catalog is loaded, so the `qt_zh_CN.qm` aggregator and its module-catalog
dependencies are not required.

Both files install to `bin/resources/translations/` in the `Translations`
component, which is included by a normal install and CPack archive. Missing
`qtbase_zh_CN.qm` warns during developer configuration and fails installation or
packaging. Build `sicnu_i18n` before installing that component. The Windows
offline bundle script builds this catalog-only target and explicitly installs
`Translations` before its `windeployqt --no-translations` step, preserving the
catalogs in a fully offline bundle.

Qt's own file-dialog labels are covered by `qtbase`; a native Windows/macOS
file-picker surface may use the OS language independently of the application's
language choice. Verify native-dialog language on the target OS separately from
Qt-widget translation checks.

## Conventions

- `%1`, `%2`, … placeholders keep their order in translations (no reordering).
- Keyboard mnemonics: English uses `&File`; the zh translation is `文件(&F)`.
- File-dialog filters keep the `;;` separator; only the display names are translated.
- RS terminology must match `data/terms/rs_glossary.json` (e.g. *radiometric
  calibration* → 辐射定标, *atmospheric correction* → 大气校正). The glossary is the
  single authority; do not invent variants in UI strings.
- The language picker keeps the endonyms `简体中文` and `English` unchanged so
  users can recognize their language in an unfamiliar interface. These two
  choice labels are an explicit exception to the English-source convention.

## The unified RS glossary (`data/terms/rs_glossary.json`)

One JSON array, one entry per concept:

```json
{
  "en": "radiometric calibration",
  "zh": "辐射定标",
  "alias": ["绝对辐射定标"],
  "definition_zh": "将传感器记录的原始量化值（DN）转换为具有物理量纲的辐射亮度或反射率的处理过程。",
  "category": "radiometric",
  "related": ["digital number", "radiance"]
}
```

- Schema: `data/terms/rs_glossary.schema.json` (12 fixed categories, `related[]` must
  reference other entries' `en` values, `en` keys are unique).
- Consumers:
  - **Help system** — `sicnu::help::TerminologyProvider` (`src/help/`) loads the glossary
    (embedded via `data/help/help_content.qrc` as `:/help/terms/rs_glossary.json`) and
    `composeHelpSystem()` derives `concept.term.*` descriptors from it. Terms are
    therefore searchable in the one help catalog — there is no second catalog and no
    content fork.
  - **Translation layer** — the same file pins the terminology used in `sicnu_zh_CN.ts`.
  - **D9 (agent)** — `TerminologyProvider::lookup(en|zh|alias)` is the direct API for
    agent answers; it reads the same file the help system uses.

When authoring glossary entries: `definition_zh` is one classroom-usable sentence —
it is what students and the agent will quote.

## Testing

`ctest -R test_i18n -j1` guards the pipeline:

| Check | What it enforces |
|---|---|
| `.ts` completeness | zero `type="unfinished"` / empty translations, ≥3000 messages, en→zh_CN languages |
| glossary integrity | ≥300 terms, zero loader errors, all 12 categories, `related[]` resolves |
| one catalog | terms appear as `concept.term.*` descriptors and are found by `HelpSearchIndex` |
| sweep audit | no widget-API string literal without `tr()` in the audited modules |

### Test expectations are pinned to the English source, never to a translation

Ordinary widget tests do not install translators, so their `tr()` calls return the
English `<source>` text. Assert that source string; where it carries a `%1`
placeholder, assert the constant prefix ahead of it. Chinese literals supplied as
test inputs, such as a filesystem path, do not depend on translation.

Translation-specific tests may explicitly install the catalogs to check language
selection, standard-widget translations and complete English fallback. Keep those
translator lifetimes isolated; do not make unrelated tests depend on the host
locale or a previous test's translator.

## Known limitations

- `QObject::tr()`-style calls in free functions use the `QObject` context; a few
  pre-existing call sites compare displayed strings against `tr()` results. This is
  safe only because the translation layer maps identical English sources to identical
  Chinese everywhere. Do not introduce per-context variants of such shared strings.
- `src/` outside `src/app` (agent, processing, …) may still carry Chinese literals;
  those surfaces are out of the D6 scope and are translated in later tracks.
