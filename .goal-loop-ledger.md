## Static proof of #1047 (confirmed by reading, not assumed)
`acquire()` tested `m_impl` and allocated `new Impl` with no synchronization; `clear()` read it unsynchronized. Two concurrent first acquires could each observe nullptr → two `Impl`s (one leaked), two mutex domains, two `handles` maps, two independent `handlesPerUrl` bounds; the `handlesPerUrl` clamp write raced with the read in the hot loop.

## Chosen fix
- Removed the raw `Impl *m_impl` member; added private `static Impl &impl()` returning a function-local static (C++11 magic-static guarantee) shared by `acquire()` and `clear()`.
- Env `SICNU_REMOTE_POOL_HANDLES` parsing/clamp moved into `Impl` construction with `const size_t handlesPerUrl`, so every reader sees a fully-published value.
- `clear()` additionally waits for in-flight opens (`opening` map drain, zero-count entries tolerated) so "drops every cached handle" is honest under concurrency.
- No public API/ABI change: `instance()/acquire()/clear()/openCount()` signatures unchanged; the removed member was private.

- [x] O2: `handlesPerUrl` bound cannot be bypassed (peak concurrent holders ≤ bound, open growth ≤ bound).
- [x] O3: acquire/clear contract explicit + tested; two consecutive full-suite passes (plus a third) green.
