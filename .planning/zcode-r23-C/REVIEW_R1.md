## Checklist notes

### A. WP-1 correctness (index math re-derived)

- **Delta branch (unchanged, verified against master)**: `first = logLinesOffset - 1` is the absolute index of the record's first line (`job_types.h:48-57`; engine sets `copy.logLinesOffset = droppedLogLines + localStart + 1` at job_engine.cpp:996 and :1114, so `first` is absolute). Skip-below-`seen` + `seen = engineIndex + 1` is monotone; identical to master (diff confirms only the cumulative branch + seam changed).
- **New cumulative branch** (`task_center.cpp:2044-2064`): authoritative/cumulative records (progress-callback copies at job_engine.cpp:1024, `startedCopy` at :858/:868, queued-cancel at :341/:402, shutdown cancels at :151-157/:172-173, submit-time catch-up snapshot at task_center.cpp:3119-3120) all carry `logLinesOffset == 0` with the retained window `[droppedLogLines, droppedLogLines + size)` — offsets are only ever set on transient delta copies, never on the stored record (verified: the only assignments are :996, :1114, :1122, all on copies). So `absTotal = droppedLogLines + size()` is the absolute appended count, and the slice `start = max(forwarded, dropped) - dropped`, `[start, size())` delivers exactly the absolute range `[max(forwarded, dropped), absTotal)`. Correct:
  - `forwarded >= dropped`: forwards precisely the not-yet-seen tail; count set to `absTotal` only under `absTotal > forwarded` ⇒ never moves backwards.
  - `dropped > forwarded` (clamping): start = 0, whole retained window forwarded, count jumps to `absTotal`. Absolute `[forwarded, dropped)` was evicted and is unrecoverable by design (#1705 bounded retention) — the delta lane has the same property (cursor `localStart` clamps to the window at job_engine.cpp:994-995). No duplication is possible.
  - **Interleavings**: both branches read and write `m_forwardedLogCounts` under the same `m_mutex` acquisition (task_center.cpp:2020-2065), so the listener thread, the submit/catch-up thread (task_center.cpp:3120) and the test seam serialize; each branch is individually monotone and both now index the SAME absolute space, so delta↔cumulative interleavings in any order (including the R2-F3 stale-cumulative-then-late-delta shape and the submit-time catch-up racing worker records) preserve exactly-once. Verified by case analysis: (cumulative[100,250) then delta[100,200)) ⇒ delta fully skipped; (delta[100,200) then cumulative[100,250)) ⇒ cumulative forwards [200,250) only; both correct.
  - **Empty `logLines`**: `dropped==0` ⇒ `absTotal==0`, guard false, no-op (historical behavior). `dropped>0` ⇒ count set to `dropped` with nothing forwarded — correct bookkeeping (nothing retained to forward).
  - **Overflow**: `droppedLogLines + size()` in `size_t`; dropped grows by ≤5 001 per 10 001 appends (job_engine.cpp:780-785) — overflow needs ~10^15 evictions. Not plausible. `max(forwarded, dropped) - dropped` cannot underflow (max-first).
  - **Pre-existing `forwarded` read** (task_center.cpp:2021): now consumed only by the else branch; harmless, and the delta branch's own `seen` re-read is the pre-existing pattern.
  - Degenerate check of the comment's claim: `dropped==0` ⇒ `start = forwarded`, slice `[forwarded, size())`, guard `size() > forwarded` — byte-for-byte the historical semantics. Comment accurate.
