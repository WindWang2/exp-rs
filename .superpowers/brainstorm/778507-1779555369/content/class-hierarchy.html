Extensibility: Core Class Hierarchy

Defining the base classes that will allow us to plug in new data types easily

Proposed Class structure (engine/core/display/)
class MapLayer (Abstract):
    - id, name, opacity, visible
    - crs, extent
    - abstract draw(painter, settings)

class VectorLayer(MapLayer):
    - provider (OGR/Shapefile)
    - renderer (Symbology)
    - draw() implementation (iterates features)

class RasterLayer(MapLayer):
    - provider (GDAL/Tiff)
    - pipe (Color ramp / Multiband)
    - draw() implementation (image rendering)

Question: The "DataProvider" Abstraction

QGIS uses a DataProvider layer to separate the file format (GDAL, PostGIS, WFS) from the Map Layer itself. Should we implement this now to support non-file sources (like web services) later?

A

Yes, include DataProviders

Decouple I/O from Layers. Best for long-term scalability (WMS, Databases).

B

No, keep it simple

Let Layers handle their own file I/O for now. Faster to implement initially.
